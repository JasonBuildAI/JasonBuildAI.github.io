01 / WHY HEARTH

The hard part is not the model.
It is everything around it.

Hearth starts from a simple admission: a convincing demo and a piece of work you can delegate for months are not the same thing.

01

State lives in chat

After a crash, restart, or device switch, task context and progress cannot be recovered reliably. You start over by explaining again.

02

Side effects have no ledger

Sending email, editing files, or pushing code lacks approvals, idempotency, and receipts. Failure is hard to reconcile, so delegation stays risky.

03

Permissions and memory blur

Credentials, personal context, and tool permissions blend together. The user cannot tell what the Agent is actually allowed to do.

04

Every task starts from zero

Context and token costs are uncontrolled, while successful work never becomes a bounded, evaluated, reversible skill.

ONE-SENTENCE DEFINITION

Hearth is a general-purpose personal Agent OS with personal context, durable execution, real tools, and multi-device entry points.

The goal is not another chat window that needs supervision, but repetitive digital labor that can be confidently delegated, verified, and recovered.

  • Single-userDesigned around one person's real workflow, not enterprise multi-tenancy.
  • Local-firstIdentity, state, and credentials stay as close to your own devices as possible.
  • Parallel executorsCodex is a powerful executor, not the product itself or the only brain.

02 / SYSTEM

One logical Agent.
Seven cooperating planes.

Hearth does not make a model the system itself. The Control Plane decides what to do, whether it is allowed, and when to interrupt. The Durable Harness owns recovery and evidence. Executors are replaceable capability layers.

Every fact enters the Event Log. Every external side effect passes through the outbox, idempotency keys, and a Receipt. Every UI state is a projection, never the source of truth.

DESIGN INVARIANT

Executors can change, devices can move, and model vendors can be swapped. The source of truth, authorization boundary, and recovery path cannot.

03 / DESIGN CHOICES

Four choices that cannot be compromised.

Together they make Hearth something more than a UI wrapped around Codex: personal infrastructure that can run for a long time and be verified.

01

Task Control Plane

Define the task, mandate, and risk before choosing who executes it. An executor never decides its own authority.

02

Durable execution

Continue after a crash, network loss, sleep, or device switch instead of starting over. Every failure leaves a reason and a recovery path.

03

Parallel executors

Choose Codex, Connector, Browser, GUI, or Human by capability, risk, and token cost rather than cramming everything into one loop.

04

Memory and evolution

Make experience safely recallable, but require provenance, evaluation, and rollback for every write, promotion, and change.

04 / TASK FLOW

From one sentence
to a verifiable receipt.

The user never needs to learn Harness, Ticket, or WorkerEvent. The system must make three things clear: what is happening, whether you are needed, and how to continue after failure.

  1. 01

    Intent

    A person, schedule, or external event produces input.

  2. 02

    Task card

    Turn intent into a clear goal, scope, and primary action.

  3. 03

    Mandate

    Policy, budget, and approvals decide what is allowed now.

  4. 04

    Execution

    The selected executor works in a restricted environment and keeps writing events.

  5. 05

    Verify & recover

    Complete, retry, switch executors, or hand off to a human, with a receipt.

05 / ROADMAP

Seven stages.
One capability ladder.

The roadmap advances by capability gates, not date promises. Every stage must deliver a visible interface, durable state, verification evidence, and a recovery path together.

  1. Stage 0Prototype & contractsCurrent starting point · product wedge, clickable prototype, schema v0
  2. Stage 1Local MVPhearthd, SQLite, Event Log, Codex, approvals, and artifacts
  3. Stage 2Daily operatorReal work across email, calendar, documents, web, and data
  4. Stage 3Desktop operatorGUI execution, device agentd, takeover, and desktop isolation
  5. Stage 4Proactive personal AgentTriggers, attention budget, mobile PWA, and device pairing
  6. Stage 5Memory & Evolution OSMemory OS, skill evaluation, promotion, and rollback
  7. Stage 6Personal Agent OS v1.0Multi-device sync, migration, long-running operation, quotas

Stage 0 is not about writing more documents. It is about pinning down the prototype, interaction, protocols, and acceptance.

06 / CURRENT STATUS

In development, with the boundaries stated.

Hearth is my personal project, not a company or team product. It is currently in the specification and roadmap stage: the product, architecture, safety, evaluation, and delivery documents are complete, while the runnable hearthd, hearth CLI, and Web interface have not yet begun.
